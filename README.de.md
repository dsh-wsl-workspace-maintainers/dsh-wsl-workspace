![alt text](image-3.png)
Füge aus der DeepSeek-Harness-Web-GUI einen WSL-Arbeitsbereich hinzu und führe die gesamte Agent-Sitzung — Bash-Befehle und Datei-Lesen/-Schreiben — innerhalb einer lokalen WSL-Distribution mit Linux-Pfaden aus. In WSL muss nichts installiert werden. Die Sitzung kann gleichzeitig auf WSL und Windows zugreifen: Bash-Befehle laufen in der WSL-Distribution, während Windows-Dateien über `/mnt/<laufwerk>` (z. B. `/mnt/c/Users/...`) erreichbar bleiben.

Die Liste der unterstützten DSH-Versionen steht im Abschnitt Compatibility von [README.md](README.md).

## Installation

Wähle eine der drei folgenden Methoden und starte danach `dsh web` neu:

```powershell
# 1) npm-Paket
dsh plugin --profile web add dsh-wsl-workspace

# 2) GitHub-Repository (enthält das vorgebaute lib/, kein lokaler Build nötig)
dsh plugin --profile web add https://github.com/dsh-wsl-workspace-maintainers/dsh-wsl-workspace

# 3) Lokales Verzeichnis (Entwicklung / eigener Gebrauch)
dsh plugin --profile web add D:\path\to\dsh-wsl-workspace
```

Nach dem Neustart von `dsh web` erscheint neben Settings am unteren Rand der Seitenleiste ein W-Button.

## Verwendung

Klicke in der Seitenleiste unten neben Settings auf den W-Button, um den Dialog „Add WSL workspace" zu öffnen. Wähle eine Distribution, durchsuche den Verzeichnisbaum oder gib einen absoluten Linux-Pfad ein (z. B. `/home/me/proj`) — mit dem Check-Button kannst du prüfen, ob der Pfad existiert. Der Dialog folgt der Sprache der DeepSeek-Harness-Oberfläche. Das Feld Benutzername ist optional: Leer lassen führt die Befehle als Standardbenutzer der Distribution aus, ein Eintrag führt die Sitzung als diesen Benutzer aus (äquivalent zu `wsl.exe -u <benutzer>`). Der Benutzername ändert nur die Ausführungsidentität des Bash-Tools — die Datei-Tools laufen über die Windows-seitige WSL-Freigabe und sind davon unberührt. Der Benutzername jedes Arbeitsbereichs liegt in `<dshHome>/wsl-workspaces.json`; lösche den Eintrag (oder erstelle den Arbeitsbereich über den Dialog neu), um zum Standardbenutzer zurückzukehren.

Klicke auf „Create & open", um eine neue Sitzung im Arbeitsbereich zu starten. In der neuen Sitzung führt das Bash-Tool Befehle in der gewählten Distribution aus, und `read`/`write`/`edit` arbeiten auf WSL-Dateien — jeder vom Modell gesehene Pfad ist ein Linux-Pfad. Der Modus-Wähler funktioniert wie gewohnt: Standard, PTC, Minimal und Creative landen automatisch auf ihrer WSL-Variante (die WSL-Varianten-Einträge im Wähler sind zweisprachig, z. B. `WSL · Standard mode（标准模式）`), und Windows-Dateien bleiben aus der Sitzung unter `/mnt/<laufwerk>` (z. B. `/mnt/c/Users/...`) erreichbar.Der „?“-Button des Dialogs öffnet ein Panel mit den DSH-Releases, die dieser Build deklariert, der Verwendung des Plugins und den Grenzen, die es nicht aushebeln kann.

## Verhaltenshinweise

- **Bash-Tool**: läuft in der WSL-Distribution als der konfigurierte Benutzername (leer = Standardbenutzer der Distribution, oft `root`) und kann daher überall in der Distribution lesen und schreiben. Die Windows-ACL-Sandbox kann `wsl.exe` nicht umhüllen — die Kindprozesse laufen auf der Linux-Kernelseite — daher ist WSL selbst die Isolationsgrenze, und die DSH-Dateipolitik gilt nicht für Bash.
- **Datei-Tools (`read`/`write`/`edit`)**: laufen über die Windows-seitige WSL-9P-Freigabe; das Benutzername-Feld betrifft sie nicht. Zwei Nähte, die der Host normalerweise liefert, sind innerhalb der WSL-Welt wiederhergestellt. **Symlinks**: die Freigabe kann einen Linux-Link zwar auflisten, aber nicht auflösen, deshalb fragen `resolve`/`lstat` die Distribution nach dem echten Pfad (`wsl.exe … readlink -f`) und arbeiten dort weiter — ein Link wird nie durch eine reguläre Datei ersetzt. **Zugriffsmodus**: `write`/`edit` werden durch `ctx.sandboxPolicy` eingehegt, exakt so wie das Host-Backend einhegt — dieselbe `writableRoots`-Allowlist (plus das `/tmp` der Distribution), dieselbe `FS_SANDBOX_DENIED`-Meldung, die die Tool-Ebene als Ablehnung darstellt, und dieselbe `sandboxMode`-Tatsache, die sie für eine Eskalation liest. Weil die Einhegung nach der Auflösung läuft, beurteilt sie den echten Pfad: ein Link aus dem Workspace hinaus ist ein Schreiben außerhalb und wird unter `workspace-write` abgelehnt. Ein Deployment ohne Policy-Service hegt nichts ein, wie auf dem Host.
- **Dateisuche (`grep`/`glob`)**: die Suchsuite des Hosts spawnt ein mitgeliefertes *Windows*-ripgrep, das einen Linux-Pfad nicht öffnen kann, also mountet die WSL-Welt ihr eigenes Gegenstück (`src/host/wsl-search.ts` → `lib/wsl-search.js`) und führt die Suche **innerhalb der Distribution** aus. Tool-Namen, Parameterschemas, Kappen, Ausgabeschema (`Line N:`-Gruppierung, Trefferzähler-Kopf, Hinweis bei erreichtem Cap), Suchkarten und das Auslagern gekürzter Ergebnisse stammen aus den exportierten Teilen von `@deepseek-ai/dsh-tool-fs-search` selbst, damit das Modell dasselbe sieht wie auf dem Host. `grep` nutzt das GNU grep der Distribution (`-rnIEH -Z`; POSIX-ERE — `\d`, `\w`, `\b` und `(?i)` funktionieren, Lookaround und Rückverweise nicht), überspringt versteckte Dateien und Verzeichnisse sowie `node_modules` wie ripgreps Default, liest **kein** `.gitignore`, und schlägt in einer Distribution ohne GNU grep laut fehl, statt unlesbare Datensätze zu rahmen. `glob` listet mit GNU `find` (`-printf` liefert die Änderungszeit jeder Datei ohne ein stat pro Datei) und gleicht gitignore-artige Muster hier im Plugin-Prozess ab (`*` überquert nie ein Trennzeichen, `**` tut es, `?`, `[...]`, `{a,b}` und ein leading `!` negiert), sortiert ältestes zuerst, genau wie `rg --sort=modified`. Beide durchsuchen direkt den Linux-Baum — Symlinks, Rechte und traversal ohne `.gitignore` inbegriffen — nie die 9P-Freigabe, und keiner folgt einem Symlink, der beim Rekursionen getroffen wird, was auch ripgreps Default ist. Modi, deren Quell-Preset keine Suchsuite mountet (Minimal), gewinnen keine dazu.
- **Skill-Katalog**: die Entdeckung startet beim nächstliegenden `.git`-Vorfahren des Session-cwd (sonst beim cwd selbst) und wandert abwärts durch `.dsh/skills` / `.agents/skills` — verschachtelte Projekte inklusive — begrenzt auf 4 Verzeichnisebenen, 64 Skill-Verzeichnisse und 4096 besuchte Verzeichnisse; registrieren Sie den Workspace also am Projektroot, in dem Sie tatsächlich arbeiten. Ein Linux-Symlink, den die Windows-seitige Freigabe nicht auflösen kann, wird über die Distribution aufgelöst (`wsl.exe … readlink -f`, höchstens 32 pro Suche, vier gleichzeitig), und der Walk arbeitet am echten Pfad weiter, sodass ein mit `ln -s` eingebundenes Projekt — samt der darunter liegenden verschachtelten Projekte — gefunden und über diesen echten Pfad dedupliziert wird. Da das Watchen eines `\wsl.localhost\...`-Pfad fehlschlägt, pinnt das generierte Preset `watch: false` auf der `skill-filesystem`-Zeile und das Plugin pollt stattdessen, in zwei Pässen: der billige Pass läuft alle 3 Sekunden über die veröffentlichten Skill-Verzeichnisse und re-statet jede Skill-Datei, weshalb eine hinzugefügte, entfernte oder **bearbeitete** Skill die nächste Modellrunde erreicht (der Stempel ist genau dafür nötig — der Katalog des Modells wird nur rebuildet, wenn sich die Revision des Registers bewegt, und ein Verzeichnislisting kann ein neu geschriebenes `SKILL.md` nicht von einer unberührten Datei unterscheiden); der vollständige Rediscovery-Walk läuft alle 30 Sekunden, weil nur ein Walk ein zuvor nicht existentes Skill-Verzeichnis finden kann. Skill-Rümpfe werden immer live geladen.
- **Shell-Lebensdauer**: `bash` ist eine **statusbehaftete** Shell — `cd`, exportierte Variablen, ein aktiviertes virtualenv und Hintergrundjobs überleben Aufrufe hinweg. Die Welt mountet die PTY-Registry des Hosts und dessen konfigurationsgesteuertes Backend (`@deepseek-ai/dsh-terminal-bash`), gerichtet auf das Relay dieses Plugins (`src/host/wsl-relay.ts` → `lib/wsl-relay.js`, vom node des Hosts ausgeführt), das das PTY an `wsl.exe … bash` übergibt: die Distribution kommt aus dem UNC-cwd der Session (sonst `DSH_WSL_DISTRO`), der optionale Benutzername aus `DSH_WSL_USER`, und das Relay führt `bash -lc 'cd … && exec bash -i'` aus, damit die Login-Umgebung geladen wird und das Sitzungsverzeichnis bestehen bleibt (ein nacktes `bash -l` kann von einem Profil nach `$HOME` geschickt werden). Das Tool registriert den Namen `bash` und ersetzt damit die Wegwerf-Zeile `dsh-tool-bash`, die ein Nicht-WSL-Preset nutzen würde; die Welt stellt außerdem ihre eigene No-op-`sandbox`-Capability bereit (`src/host/wsl-sandbox.ts`), weil der Windows-ACL-Runner des Hosts den Sicherheitsdeskriptor eines `\wsl.localhost\…`-Pfads nicht lesen kann und der PTY-Backend vor dem Spawnen durch ihn einkapselt. Beide Shells laufen in der Distribution und liegen außerhalb der DSH-Dateipolitik — WSL ist ihre Isolationsgrenze. **Zwei Folgen des Host-Wrappings stehen in der Tool-Beschreibung**: die Shell ist ein Prozess für den ganzen Agenten, deshalb entscheidet ein `cd` in einem Aufruf, wo der nächste startet — nutzen Sie absolute Pfade oder ein explizites `cd`; und der Host verpackt jeden Befehl als `eval -- $'…'`, weshalb ein Befehl, der mit `&` endet, **die komplette verpackte Befehlszeile** in den Hintergrund stellt — der Aufruf kehrt sofort mit Exit-Code 0 und ohne Ausgabe zurück, während die echte Ausgabe später eintrifft, möglicherweise in der Ausgabe des nächsten Aufrufs. Schreiben Sie Hintergrundarbeit als `( langes-job > log 2>&1 ) &` in einer eigenen Zeile, oder nutzen Sie das Hintergrundjob-Tool.
- **In ein Terminal tippen (`wsl_terminal`)**: In eine Pipe kann man nicht tippen, also hatte ein Programm, das eine Frage stellt — `sudo` mit Passwortabfrage, `ssh` mit dem Fingerabdruck der ersten Verbindung, ein REPL, ein Editor, eine TUI —, keine Antwort, die der Agent geben konnte: Die Wartezeit wurde diagnostiziert, gestoppt und auf einem Wegwerf-Pseudoterminal erneut ausgeführt, nur damit das Modell die Beschwerde des Programms lesen konnte — den Rest musste ein Mensch übernehmen. Jetzt mountet die Welt eine Tür, durch die der Agent tippen kann: `open` startet ein interaktives Terminal, `send` tippt Text (standardmäßig mit Enter, `submit: false` tippt nur), `read` blättert im erhaltenen Bildschirm, `signal` liefert `SIGINT`/`SIGTERM`/`SIGKILL`/`SIGTSTP`/`SIGHUP` (`SIGINT` ist Strg-C), `close` beendet und `list` meldet, was offen ist. Es ist die PTY-Registry des Hosts samt `dsh-terminal-bash`-Backend, gerichtet auf das Relay dieses Plugins — dieselbe Mechanik hinter dem Terminal-Tab der rechten Seitenleiste, nur mit dem Agenten an der Tastatur statt eines Menschen — und die gestartete Shell läuft als **der im Workspace konfigurierte Benutzer**, zurückgelesen aus dem Workspace-Speicher, weil der Host die Umgebung eines PTY-Kindes selbst baut und dabei jede `DSH_*`-Variable verwirft. Das Pipe-`bash` oben bleibt für alles andere der Standard: Die Pipe trägt jedes Byte, während ein Terminalbildschirm ein 160-Spalten-Rendering mit begrenztem Scrollback ist. Drei Kosten werden genannt statt verborgen: Das Ruhefenster des Backends sinkt von standardmäßig 3000 ms auf 1200 ms (Quellenhinweis in `src/host/variants.ts`), sodass ein Sendevorgang, dessen Prompt der Host nicht erkennt, in ~1,2–1,8 s zurückkommt statt in ~3,0–3,6 s; ein `send` sagt, welcher der beiden Fälle eingetreten ist, statt einen stillen Bildschirm als Prompt auszugeben; und alles Getippte ist Teil der Gesprächsaufzeichnung, ein Passwort muss also vom Benutzer kommen. Auf einer echten Distribution gemessen, beide Build-Ebenen, als `root` und als `ruler` (66/66 Zellen in `bash-session-real`): `open` 477–490 ms, ein getippter Befehl antwortet, **ein Tastendruck erreicht ein auf `/dev/tty` blockiertes Programm** (`GOT=…`), `submit: false` tippt ohne auszuführen und das nächste Enter führt aus, `SIGINT` beendet ein `sleep 30` und die Shell überlebt, `close` lässt kein `bash -i` zurück.
- **Verfolgbare Hintergrundjobs**: `bash_background` startet einen Befehl im Hintergrund und gibt sofort eine Job-Id aus dem Register zurück; danach arbeiten `job_list`, `job_output` (inkrementelles Lesen, Statusübergänge, Fertig-Meldungen) und `job_kill` des Hosts damit wie gewohnt. Die Zeile existiert, weil das Schema der persistenten Shell nur `command` deklariert: ohne einen Erzeuger antwortete `job_list` immer „no background jobs“, und ein an `bash` übergebenes `run_in_background: true` wurde stillschweigend ignoriert — das Parameterschema verbietet zusätzliche Eigenschaften nicht, also meldete sich nichts. Eine echte Session hat genau das gefunden. Das Tool wird nur zusammen mit der persistenten Shell gemountet; eine Welt, die die Wegwerf-bash-Zeile behält, hat `run_in_background` bereits an diesem Tool.
- **Ältere Hosts fallen auf eine Wegwerf-Shell zurück**: der persistente Stack ist Code des *Hosts*, und auf Windows braucht er einen Plattform-Prozessinspektor, den es erst ab `0.1.0-rc.8` gibt — in `0.1.0-rc.7` wirft `spawnTerminal` `subprocess-local: terminal inspection is unsupported on platform win32`, bevor irgendein Prozess startet, weshalb in jenem Release jeder einzelne `bash`-Aufruf fehlschlägt (grep/glob, die nie das PTY berühren, funktionieren weiter). Das Plugin *prüft* deshalb beim Start den Untergrund, statt etwas anzunehmen: es gibt `spawnTerminal` ein Programm, das nicht existieren kann, was nur die Inspektor-Prüfung erreicht und sonst nichts — es wird weder der eine noch der andere Prozess erzeugt, und die Ablehnung sagt, welche Hälfte fehlte. Wenn die Antwort „kein Inspektor“ lautet, behält die generierte Welt die Wegwerf-Zeile `dsh-tool-bash` (der eigene `ctx.shell`-Provider des Plugins, ohne PTY), und das Modell bekommt eine funktionierende, statuslose Shell statt eines Fehlers bei jedem Aufruf. `0.1.0-rc.7` ist der einzige deklarierte Release in diesem Zustand; jeder spätere bekommt die persistente Shell.
- Das verzerrte `localhost`-Port-Forwarding-Banner, das `wsl.exe` auf stderr ausgibt, wenn die Distribution noch nicht lief, ist harmlos.
