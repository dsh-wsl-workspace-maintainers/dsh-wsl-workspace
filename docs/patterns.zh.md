# 三套对照装置：故意红账本、故障可见性、差异账本

> **这份文件是什么**：本仓库把三类隐性知识写成"代码能读的声明"的三套做法——已知的失败
> （故意红账本）、一帧里发生过的失败（故障可见性）、与原生 `bash` 的差异（差异账本）。
> 两套账本共享同一个形状：**先声明**、**再有一道会失败的闸逐条比对**、**两个方向都失败**——
> 现实里多出来的，和声明过的却消失的，都是红。
>
> **谁在读它**：没有闸门把这份说明当判据（`npm run test:docs` 只检查它的相对链接能不能解析）。
> 三套装置的规则本体分别住在 [`tests/deliberate-reds.mjs`](../tests/deliberate-reds.mjs)、
> [`scripts/run-seams.mjs`](../scripts/run-seams.mjs)、
> [`.github/workflows/ci.yml`](../.github/workflows/ci.yml)、[`bash-parity.md`](./bash-parity.md)，
> 与它们冲突时以它们为准；每道闸的本地命令和 CI 归属在
> [`CHECK-CATALOG.md`](./CHECK-CATALOG.md)。
>
> **谁该读**：准备动账本、动 CI、或给 `bash` 加参数与改输出的人；以及想知道
> "这里为什么长成这样"的新贡献者。

## 1. 故意红账本：已知的红有主人、有欠条、有修法

**问题。** 库里总有些断言在某些形状的机器上就是红：一个系统调用在 runner 上行为不一致、
一个还没到修的时候的技术债、一个只在 WSL1 成立的读取差异。传统处理是 `skip`、忽略、
或一句 `// TODO`——两个灾难跟着来：**技术债被静默吞掉**（三个月后没人知道那条 skip
是什么意思），以及**测试突然绿了却没人知道为什么**（环境升级了？改坏了别的东西？
还是测试本身写错了？三个结论完全不同，"绿"在这里比"红"更危险）。

**机制。** 账本在 [`tests/deliberate-reds.mjs`](../tests/deliberate-reds.mjs)：一条 = `id`、
所在套件、`prefix`（与套件自己打印的失败行做的事面子串匹配）、**每个机器形状**
（`win32`＝维护者机器 / `posix`＝ubuntu runner）各自的期望（`red` 或 `skip`）、
`debt`（欠什么）、`repair`（怎么还）。缺其中任何一项的条目不合法——一条没有修法的红
是噪声，不是复现。

闸在 [`scripts/run-seams.mjs`](../scripts/run-seams.mjs)（`npm run test:seams`）：先把三个套件
（`route-envelope`、`search-run-fakes`、`tech-debt-exposure`）各跑一遍、**逐行原文打印**
（每个 `not ok:` / `✖` / `SKIP:` 都印出来，不压制任何失败），再把观测到的红集合与账本对照——
三个方向都会失败：

- **未声明的新红** → 失败（"a red nobody owns: fix it or add it … with its debt and repair"）；
- **声明过的红消失**（转绿，或变成 skip）→ 失败——有人修了产品，欠这个文件一次编辑；
- **红的形状变了**（账本说在 win32 红、这次在 posix 红；或 skip 行本身不见了）→
  失败（moved premise）。

判决只由三件事组成（missing / 未声明红 / moved 全空才退出 0）；**未声明的 skip
只打印一行警告**（`ledger: undeclared skip`），不改判决——这是这套闸里唯一不进判决的格子，
写在这里，免得它被读成"已经被管住了"。

机制自己也有控制：[`tests/deliberate-reds.test.mjs`](../tests/deliberate-reds.test.mjs)
用**自带的合成账本**把上面每个方向正演一遍（未声明红被点名、转绿被抓、形状搬移被抓、
skip 行消失被抓、未知形状被拒）。它**不读真实账本**——读了的控制会在每还清一条债时
同时少一条，本项目为此改过一次。[`run-seams.mjs`](../scripts/run-seams.mjs) 里还有一个
免费的活体对照：`DSH_SEAM_SHAPE=posix` 把同一份观测按另一种形状读，必须判 MOVED——
证明闸门对"前提变化"有反应，而不只对合成夹具。

**现状与效果。** 账本今天是**空的**：它记过的十条债全部还清（#65），机制留了下来——
一帧接一帧，任何一条没人声明的新红仍会让 `test:seams` 红。这十条包括 `check` 把每个
`stat` 失败折进 `{exists:false}`（#44 §6）、NUL 嗅探把 NUL 分隔的 UTF-8 流解成双倍长度的
乱码、三个把参数表交给命令解释器的调用点。

它换来一笔关键交易。本项目的验收面是"云上 checks 绿"，而一帧**注定红**的 CI 是个不能报警的
报警器；#46 把一批"必须保持红"的复现带进 CI 时，闸就从"套件过没过"换成了
"**红集合恰好等于声明集合**"——红保住了，报警也保住了。

**维护者视角。** 它解决的是"已知的失败"与"未知的失败"怎么区分，并让前者不许悄悄变成后者；
修债必须与改账本在同一个提交里（[standards.zh.md](./standards.zh.md) 的 S3）。

## 2. 故障可见性：一帧把话说全

**问题。** 默认的 CI 是"第一个失败即止"：一个步骤红，它后面同 job 的步骤全部变成 `skipped`。
两个代价：你只拿到第一个问题，改完再推、再等一轮（`wsl-gate` 一帧的 job 上限就是 35 分钟）；
更坏的形态是**一个注定红的步骤站在中间**，把它身后所有门禁一起消音——它红的时候，
别的门禁等于没跑。

**机制。** 三件装置，都在 [`.github/workflows/ci.yml`](../.github/workflows/ci.yml)：

1. **同一 shell 里的一串 gate，用 `run_one` 包起来。** src / lib 两个 plane 的 gate 步骤
   （十来个 driver 挤在同一个 step 里）中，每个 driver 都经 `run_one`（lib 侧是 `run_lib`）
   执行：输出各写 `logs/<name>.log`，打印 `rc=` 与 **`elapsed=`**（bash 的 `$SECONDS`），
   再打该 gate 自己的判决行（`checks passed` / `FAIL`）与尾部 6 行——`bash-session-real`
   例外，打全份日志，因为它每一格都带毫秒数，那是阈值类问题的唯一读数。`run_one`
   永远 `return 0`，一个 driver 红不挡下一个；整段跑完才 `exit $FAIL`。
   两个配套细节都是被真实帧逼出来的：所有守卫必须写成复合语句（`|| { … }`），
   因为 GitHub 的 bash 跑在 `-e` 下，第一处红会杀掉循环、剩下的 gate 全部熄灭
   （frame 3 里实测过一次）；`elapsed=` 是"215 秒都花在哪里"这个问题曾必须下载四个日志工件
   才能回答之后加的——现在下一帧一行就说清：`elapsed=153s` 属于 `bash-session-real`
   （[ci-speed-0.7.7.md](./ci-speed-0.7.7.md) §1、§3）。
2. **注定红的那一步放最后。** `runtime-tests` 的 seam 账本步骤（`npm run test:seams`）
   排在全 job 最后一位，理由写在它自己的注释里："A failing step skips everything after it"——
   frame 36797162445 里它站在中间，`typecheck` 与 `verify:install` 双双 `skipped`。
   已知红可以是这一帧的判决，但不许当后面门禁的消音器。
3. **证据始终收集。** plane 归属校验用 `if: always()`（红了的 gate 也要拿到"我加载了哪个
   plane"的核对），失败时 postflight 抓 9P 共享的状态，日志工件 `if: always()` 上传。

**边界（它治不了什么）。** GitHub 的 step 语义不会被消灭：同一个 job 里，前一步红仍会跳过后面的
step。这里的做法不是消除它，而是把它摆对位置——注定红或最要紧的步骤放最后；一串必须互相隔离的
gate 住进同一个 shell、交给 `run_one`。job 之间按成本排序：两个重 job 都 `needs` 最便宜的
`lint-build`——那 18 秒的闸替它们拦住"提交的 `lib/` 不是这份 `src/` 造出来的"那种帧，
一帧里省回约 25 分钟的 windows 机时（[ci-speed-0.7.7.md](./ci-speed-0.7.7.md) §4）。

**效果。** 一次失败到手的是这一帧的全貌——每个 gate 的 rc、耗时、判决行和它的尾巴——
而不是"第一个红"；归因在本地可读的步骤日志里完成，不用先下载工件。

**维护者视角。** 不怕测试红，怕的是红了不知道为什么；以及一个红把后面的信息全部挡住。

## 3. 差异账本：与宿主 `bash` 的每一处不同，都写在纸上、被代码读

**问题。** 本插件给模型挂的是一个**会话 `bash`**，替代宿主的 `bash` 工具，两者不可能完全一样：
有些不同是**故意的**（多出 `tty`、`stdin` 参数，超时后重启 shell，后台作业跑在自己的进程里），
有些是**环境使然**（WSL1 的内核不回答"这个进程是不是在等键盘"），有些是**还没验证**的。
两条烂路：假装没有差异，直到用户踩坑；把"已知差异"写在散文里，随后和代码脱节。

**机制。** 账本是 [`bash-parity.md`](./bash-parity.md)：一行一个差异，列是
`id | kind | difference | whose behaviour | what the user sees | verdict`。`kind` 只有两种——
`api`（两边**声明面**的差异：参数键、输出臂、字段名）和 `behaviour`（真跑起来的差异）；
`verdict` 以 `keep`（故意保留，附理由）或 `aligned`（已对齐，可带日期）开头。
**读这张表的是两个闸：**

- [`tests/wsl-bash-parity.test.ts`](../tests/wsl-bash-parity.test.ts)（离线，`test:node` 桶）：
  从**装着的那份宿主包**里解析出它的参数键与输出字段，和我们注册的工具比——发现差异而表里
  没有行 → 红；某行说 `aligned` 而两边实际仍不一致 → 红。宿主包不可用时它印一条响亮的
  `NOT VERIFIED`，不装死。
- [`scripts/compatibility/bash-parity-real.mjs`](../scripts/compatibility/bash-parity-real.mjs)
  （真发行版上跑）：让两个世界（宿主的**一次性**工具、我们的**会话**工具）跑同一个探测脚本，
  逐字段比签名——kind、退出码与信号、timedOut、截断、溢写文件行数、模型会读到的标记、正文——
  差异没有行 → 红；行说 aligned 却有差异 → 红；**行声明有差异、两边却答得一模一样 → 红**
  （"the ledger still says they differ"：去更新账本，不是删行）。
  仪器自己带控制：`--self-test` 不需要发行版，就能证明它会对"没写完的文件"和"永不收敛的一对"
  给出正确判决；CI 在真跑之前先跑它。

**这一格是怎么变硬的（真实读数）。** 溢写行数这一格吃过同型的假红：读到的文件还没写完，
半截行数被印成产品差异——代码注释记下了三次读数（197,852 / 193,756 / 198,437 行），
而 frame 37892642235 那次的细节行给出了证据：文件 "still for a second after 1039 ms"，
之后还在长。判据因此从**等它安静**换成**等不变量**——两个世界跑的是同一条命令，两份溢写文件
必须装同样的字节，等它们相等；等不到就报"这次读不到"，不许把半截文件印成差异（#74）。

**行不是装饰。** `param-tty`（我们有、宿主没有——"三种到终端的方式"必须可以只要管道）；
`behaviour-overstrike`（`man` 在 pty 上写的 `N\bNA\bAM\bME\bE` 被折回文本再交给模型）；
`behaviour-keyboard-wait`（一条等键盘的命令怎么被读出来、停掉、换伪终端再跑一遍——
sudo 那次 2 412 ms 带着 sudo 自己的话回来）。**对齐也是断言**：带日期的 `aligned` 行
（`param-run_in_background`、`behaviour-spill-shape`、`behaviour-workdir-relative`）是
"已实测相同"的承诺，漂移任何一条都会红。`wsl_terminal` 故意不在表里：它不是与宿主 `bash`
的差异，是这个宿主世界没有的能力。

**维护者视角。** 不需要做到 100% 一致；需要的是明确声明哪些不一致是故意的、哪些是环境使然、
哪些还没验——而且这张声明由代码来读，不是由人来读。

## 总结：同一形状，各管一类

两套账本共享同一个形状：**先声明，再有一道会失败的闸逐条比对，两个方向都失败**——
现实里多出来的、声明过的却消失的，都是红。故障可见性不是账本，它是这套形状能站住的地基：
没有"一帧把话说全"，账本的读数就只是运气。

- **故意红账本**：已知的失败有主人、有欠条、有修法；它还第一时间发现"债还了、账本没改"。
- **故障可见性**：一帧里所有 gate 的判决一起到手；注定红与最要紧的步骤不许挡住别人。
- **差异账本**：与原生行为的不同都有名字、有归属、有判决；"一致"本身也是被断言的。

它们不消灭 bug。它们让"现状"和"意图"分开的那一刻立刻可见——在代码里，不在记忆里。
