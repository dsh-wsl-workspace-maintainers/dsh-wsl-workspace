![alt text](image-3.png)
Добавьте рабочее пространство WSL из веб-интерфейса DeepSeek Harness и запустите всю сессию агента — команды bash и чтение/запись файлов — внутри локального дистрибутива WSL с путями в формате Linux. Ничего не нужно устанавливать внутри WSL. Сессия может одновременно обращаться и к WSL, и к Windows: команды bash выполняются внутри дистрибутива WSL, а файлы Windows остаются доступными через `/mnt/<диск>` (например `/mnt/c/Users/...`).

Список поддерживаемых версий DSH — в разделе Compatibility файла [README.md](README.md).

## Установка

Выберите один из трёх способов ниже, затем перезапустите `dsh web`:

```powershell
# 1) npm-пакет
dsh plugin --profile web add dsh-wsl-workspace

# 2) Репозиторий GitHub (включает предсобранный lib/, локальная сборка не нужна)
dsh plugin --profile web add https://github.com/dsh-wsl-workspace-maintainers/dsh-wsl-workspace

# 3) Локальная папка (разработка / личное использование)
dsh plugin --profile web add D:\path\to\dsh-wsl-workspace
```

После перезапуска `dsh web` рядом с Settings внизу боковой панели появится кнопка W.

## Использование

Нажмите кнопку W рядом с Settings внизу боковой панели, чтобы открыть диалог «Add WSL workspace». Выберите дистрибутив, просмотрите дерево каталогов или введите абсолютный путь Linux (например `/home/me/proj`) — кнопка Check проверяет существование пути перед созданием. Язык диалога следует языку интерфейса DeepSeek Harness. Поле имени пользователя необязательно: оставьте его пустым, чтобы выполнять команды от пользователя дистрибутива по умолчанию, или укажите пользователя Linux этого дистрибутива, чтобы сессия выполнялась от его имени (эквивалент `wsl.exe -u <пользователь>`). Имя пользователя меняет только учётную запись, под которой работает инструмент bash, — инструменты файлов идут через общую папку WSL со стороны Windows и не зависят от него. Имя пользователя каждого рабочего пространства хранится в `<dshHome>/wsl-workspaces.json`; удалите запись (или пересоздайте рабочее пространство через диалог), чтобы вернуться к пользователю по умолчанию.

Нажмите «Create & open», чтобы запустить новую сессию в рабочем пространстве. В новой сессии инструмент bash выполняет команды внутри выбранного дистрибутива, а `read`/`write`/`edit` работают с файлами WSL, поэтому каждый путь, который видит модель, — это путь Linux. Выбор режима работает как обычно: Standard, PTC, Minimal и Creative автоматически попадают на свой вариант WSL (записи вариантов WSL в селекторе двуязычные, напр. `WSL · Standard mode（标准模式）`), а файлы Windows остаются доступными из сессии через `/mnt/<диск>` (например `/mnt/c/Users/...`).Кнопка «?» в диалоге открывает панель с релизами DSH, которые объявляет эта сборка, с тем, как пользоваться плагином, и с ограничениями, которые он не может обойти.

## Примечания о поведении

- **Инструмент bash**: выполняется внутри дистрибутива WSL под настроенным именем пользователя (пусто = пользователь по умолчанию, часто `root`), поэтому может читать и писать в любом месте дистрибутива. Песочница Windows ACL не может обернуть `wsl.exe` — его дочерние процессы работают на стороне ядра Linux — поэтому сама WSL является границей изоляции, и политика файлов DSH не применяется к bash.
- **Инструменты файлов (`read`/`write`/`edit`)**: идут через WSL 9P-общую папку со стороны Windows, и поле имени пользователя на них не влияет. Два шва, которые обычно поставляет хост, восстановлены внутри WSL-мира. **Символические ссылки**: общая папка умеет перечислять Linux-ссылку, но не разрешать её, поэтому `resolve`/`lstat` спрашивают у дистрибутива реальный путь (`wsl.exe … readlink -f`) и продолжают работу от него; ссылка никогда не заменяется обычным файлом. **Режим доступа**: `write`/`edit` ограждаются через `ctx.sandboxPolicy` ровно так, как их ограждает бэкенд хоста — тот же allow-list `writableRoots` (плюс `/tmp` дистрибутива), то же `FS_SANDBOX_DENIED`, которое слой инструментов показывает как отказ, и тот же факт `sandboxMode`, который он читает для эскалации. Поскольку ограждение выполняется после разрешения, оно судит реальный путь: ссылка за пределы рабочей области — это запись вне её, и при `workspace-write` она отклоняется. Развёртывание без сервиса политики ничего не ограждает, как и на хосте.
- **Поиск по файлам (`grep`/`glob`)**: поисковый комплект хоста запускает упакованный *Windows* ripgrep, который не может открыть Linux-путь, поэтому WSL-мир монтирует собственного двойника (`src/host/wsl-search.ts` → `lib/wsl-search.js`) и выполняет поиск **внутри дистрибутива**. Названия инструментов, схемы параметров, лимиты, схема вывода (группировка `Line N:`, заголовок со счётчиком, пометка о достижении лимита), карточки поиска и выгрузка усечённых результатов берутся из экспортируемых кусочков самого `@deepseek-ai/dsh-tool-fs-search`, так что модель видит то же, что и на хосте. `grep` использует GNU grep дистрибутива (`-rnIEH -Z`; POSIX ERE — `\d`, `\w`, `\b` и `(?i)` работают, lookaround и обратные ссылки нет), пропускает скрытые файлы и каталоги и `node_modules`, как делает ripgrep по умолчанию, **не** читает `.gitignore` и громогласно падает в дистрибутиве без GNU grep, вместо того чтобы выдавать неразборчивые записи. `glob` перечисляет через GNU `find` (`-printf` даёт mtime каждого файла без отдельного stat) и сопоставляет здесь, в процессе плагина, паттерны в стиле gitignore (`*` не пересекает разделитель, `**` пересекает, `?`, `[...]`, `{a,b}`, ведущий `!` отрицает), сортируя от старых к новым ровно как `rg --sort=modified`. Оба ищут прямо по дереву Linux — включая символьные ссылки, права и обход без `.gitignore` — никогда по 9P-папке, и ни один не идёт по символьной ссылке, встреченной при рекурсии, что тоже является поведением ripgrep по умолчанию. Режимы, чей исходный пресет не монтирует поисковый комплект (Minimal), ничего не получают.
- **Каталог скиллов**: обнаружение стартует от ближайшего `.git`-предка cwd сессии (или от самого cwd, если предка нет) и сканирует вниз `.dsh/skills` / `.agents/skills`, включая вложенные проекты, с ограничением в 4 уровня каталогов, 64 каталога скиллов и 4096 посещённых каталогов — регистрируйте рабочую область у корня того проекта, в котором вы работаете. Linux-ссылку, которую не может разрешить общая папка со стороны Windows, плагин разрешает через дистрибутив (`wsl.exe … readlink -f`, не больше 32 за поиск, четыре одновременно), и обход продолжается от реального пути, поэтому проект, подвешенный через `ln -s`, — как и вложенные под ним проекты — обнаруживается и дедуплицируется по этому реальному пути. Наблюдение за путём `\wsl.localhost\...` не работает, поэтому сгенерированный пресет фиксирует `watch: false` на строке `skill-filesystem`, а плагин опрашивает сам, в два прохода: дешёвый проход раз в 3 секунды проходит по опубликованным каталогам скиллов и перезасчитывает каждый файл скилла, поэтому добавленный, удалённый или **изменённый** скилл попадает в следующий ход модели (метка времени нужна именно из-за изменений — каталог модели перестраивается только когда меняется ревизия реестра, а листинг каталога не отличает переписанный `SKILL.md` от нетронутого файла); полный обход переобнаружения идёт раз в 30 секунд, потому что только обход способен найти каталог скиллов, которого раньше не было. Тела скиллов всегда читаются вживую.
- **Время жизни шелла**: `bash` — **состоятельный** шелл: `cd`, экспортированные переменные, активированный virtualenv и фоновые задачи переживают вызовы. Мир монтирует PTY-реестр хоста и его бэкенд с настройкой через конфиг (`@deepseek-ai/dsh-terminal-bash`), направленный на relay этого плагина (`src/host/wsl-relay.ts` → `lib/wsl-relay.js`, запускаемый node самого хоста), который передаёт PTY команде `wsl.exe … bash`: дистрибутив берётся из UNC-cwd сессии (иначе из `DSH_WSL_DISTRO`), необязательное имя пользователя — из `DSH_WSL_USER`, и relay выполняет `bash -lc 'cd … && exec bash -i'`, чтобы загрузить окружение логина и при этом сохранить каталог сессии (обычный `bash -l`profile может вернуть в `$HOME`). Инструмент регистрирует имя `bash` и потому заменяет строку `dsh-tool-bash` с одним запуском, которую использовал бы не-WSL пресет; мир также предоставляет собственную no-op возможность `sandbox` (`src/host/wsl-sandbox.ts`), поскольку Windows ACL-раннер хоста не может прочитать дескриптор безопасности пути `\wsl.localhost\…`, а PTY-бэкенд ограничивает через неё до запуска процесса. Оба шелла работают внутри дистрибутива и вне политики файлов DSH — сама WSL и есть их граница изоляции. **Два следствия обёртки хоста записаны в описании инструмента**: шелл — один процесс на весь Агент, поэтому `cd` в одном вызове решает, с чего начнётся следующий — используйте абсолютные пути или явный `cd`; и хост оборачивает каждую команду как `eval -- $'…'`, поэтому команда, оканчивающаяся на `&`, уводит в фон **всю обёрнутую команду** — вызов сразу возвращает код 0 без вывода, а настоящий вывод приходит позже, возможно внутри вывода следующего вызова. Фоновую работу пишите отдельной строкой в виде `( долгая-задача > log 2>&1 ) &` или используйте инструмент фоновых задач.
- **Ввод в терминал (`wsl_terminal`)**: в канал (pipe) вводить нельзя, поэтому программе, которая задаёт вопрос — `sudo`, просящий пароль, `ssh` с отпечатком первого подключения, REPL, редактор, TUI — агенту нечего было ответить: ожидание диагностировалось, процесс останавливался и перезапускался на одноразовом псевдотерминале лишь затем, чтобы модель прочитала жалобу самой программы, а дальше всё брал на себя человек. Теперь мир монтирует дверь, через которую агент печатает: `open` открывает интерактивный терминал, `send` вводит текст (по умолчанию с Enter, `submit: false` — только текст), `read` листает сохранённый экран, `signal` доставляет `SIGINT`/`SIGTERM`/`SIGKILL`/`SIGTSTP`/`SIGHUP` (`SIGINT` — это Ctrl-C), `close` закрывает, `list` сообщает, что открыто. Это PTY-реестр хоста и его бэкенд `dsh-terminal-bash`, направленные на relay этого плагина — та же механика, что стоит за вкладкой терминала в правой панели, только за клавиатурой агент, а не человек; запускаемый шелл работает под **пользователем, заданным в рабочем пространстве**, прочитанным из хранилища рабочего пространства, потому что хост сам собирает окружение PTY-потомка и выбрасывает из него все переменные `DSH_*`. Канальный `bash` выше остаётся по умолчанию для всего остального: канал несёт каждый байт, тогда как экран терминала — это 160-колоночная отрисовка с ограниченным скроллбэком. Три издержки названы, а не спрятаны: окно тишины бэкенда снижено с 3000 мс по умолчанию до 1200 мс (примечание об источнике — в `src/host/variants.ts`), поэтому отправка, приглашение которой хост не распознал, возвращается за ~1,2–1,8 с вместо ~3,0–3,6 с; `send` говорит, какой из двух случаев произошёл, вместо того чтобы выдавать тихий экран за приглашение; и всё напечатанное входит в запись разговора, поэтому пароль должен прийти от пользователя. Измерено на реальном дистрибутиве, обе плоскости сборки, как `root` и как `ruler` (66/66 ячеек в `bash-session-real`): `open` 477–490 мс, введённая команда отвечает, **нажатие доходит до программы, заблокированной на `/dev/tty`** (`GOT=…`), `submit: false` печатает без выполнения, а следующий Enter выполняет, `SIGINT` завершает `sleep 30` и шелл выживает, а `close` не оставляет ни одного `bash -i`.
- **Отслеживаемые фоновые задачи**: `bash_background` запускает одну команду в фоне и немедленно возвращает id задачи из реестра; дальше `job_list`, `job_output` (инкрементальное чтение, переходы состояний, уведомления о завершении) и `job_kill` хоста работают с ней как обычно. Эта строка существует потому, что схема постоянному шеллу объявляет только `command`: без производителя `job_list` всегда отвечал «no background jobs», а аргумент `run_in_background: true`, переданный в `bash`, молча игнорировался — схема параметров не запрещает дополнительные свойства, поэтому ошибка никак не сообщалась. Реальная сессия наткнулась ровно на это. Инструмент монтируется только вместе с постоянным шеллом; миру, который сохраняет строку одноразового bash, `run_in_background` уже даёт тот инструмент.
- **Старые хосты откатываются к шеллу с одним запуском**: постоянный стек — это код *хоста*, и на Windows ему нужен платформенный инспектор процессов, который существует только с `0.1.0-rc.8` — в `0.1.0-rc.7` `spawnTerminal` бросает `subprocess-local: terminal inspection is unsupported on platform win32` до запуска любого процесса, поэтому каждый вызов `bash` в том релизе не работает вообще (grep/glob, которые не трогают PTY, продолжают работать). Поэтому плагин при старте *прощупывает* основание, а не исходит из предположения: он передаёт `spawnTerminal` программу, которая не может существовать, — это доходит только до проверки инспектора и больше никуда; процесс не создаётся ни в одном из случаев, а отказ говорит, какая половина подвела. Когда ответ — «инспектора нет», сгенерированный мир сохраняет строку `dsh-tool-bash` с одним запуском (собственный `ctx.shell`-провайдер плагина, без PTY), и модель получает работоспособный шелл без состояния вместо ошибки на каждый вызов. `0.1.0-rc.7` — единственный объявленный релиз в таком состоянии; все последующие получают постоянный шелл.
- Искажённый баннер пересылки порта `localhost`, который `wsl.exe` печатает в stderr, когда дистрибутив ещё не был запущен, безвреден.
